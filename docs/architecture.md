# Architecture

Mosa is one Next.js App Router application. Server Components read the SQLite catalog through `src/features/catalog/queries.ts`; route handlers validate mutations, and provider adapters normalize Xtream, M3U and existing Stalker entries. The ignored `data/` directory contains the SQLite database and encryption key; back them up together.

Each profile has at most one provider. Migration `0002` maps existing providers to profiles without changing media IDs, favorites, history or progress. The active profile is stored in `preferences`; playback, search, categories, history and profile preferences use that selection. Switching profiles reloads the page to release the persistent player. `content_restrictions` identifies categories or channels blocked for one profile/provider; queries and direct playback apply the same SQL visibility condition. Newly imported adult-labeled categories are blocked by default, and Settings provides bounded searches to manage blocks. Episode requests must first resolve a visible parent series.

Source credentials are encrypted at rest. The editing page includes server and username but not the saved password; an owner-only no-store endpoint returns the password only after the eye button is selected. Playback resolution produces an explicit URL at request time, with the profile's Xtream format default overridden by an optional source preference. Provider refresh updates known metadata in place. The source's catalog is not deleted on profile switch or QR replacement: replacement archives the old provider in a new profile. Explicit profile/source deletion is destructive and must be treated separately from switching or replacement.

Owner login and read-only viewer sessions can be configured for a trusted HTTPS reverse proxy while the application remains loopback-bound. Device pairing and provider provisioning are distinct: the device QR grants a revocable viewer session; the provider QR carries a single-use 12-minute token in the URL fragment, not an account session. The provider form submits limited Xtream or remote M3U configuration over protected HTTPS; the server hashes tokens, rate-limits submissions, encrypts pending payloads, and requires an owner to approve or reject them. Approval imports with the ordinary adapters and removes the pending encrypted payload. A configured public origin is not a substitute for a reachable protected HTTPS proxy; credentials in browser playback URLs and DNS rebinding remain important deployment risks.

The persistent playback shell is mounted at the locale layout boundary. Live TV transfers into it when floating mode is selected and restarts on handoff. Playback still depends on provider codecs, CORS, permissions and available media endpoints. The network panel reports only host and sanitized error information, not credentials; it may request at most two visible sample streams with a small byte range and short timeout, recording a provider-scoped ready/warning/error result. This checks server responses, **not** browser decoding or CORS. Source mutations invalidate health and reload the shell to release stale playback. The installable PWA has no service worker caching private URLs, video or API responses.

The movie/series catalog has its own scroll container; selecting a title resets that container and focuses the inline detail heading. Season accordions are local UI state and start closed. Xtream movie details are fetched only when a selected movie lacks a description; failures leave the imported catalog usable. For `.ts` direct playback, the browser reads a small leading byte range and requires TS sync bytes or an FLV header before initializing mpegts.js. Failed checks advance to the existing alternate source; they do not imply that the alternate will play in every browser.
